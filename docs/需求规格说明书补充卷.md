## 一、需求收集

本项目没有外部委托客户，需求不是从访谈中得来，而是从三个方向推导：交付方向的产品定位约束、目标用户群体的公开调研数据、现有同类工具的能力缺口。本节把推导链条固定下来，使每一条需求都可以回溯到它的来源。

### （一）利益相关者

| 角色 | 关注点 | 对需求的影响 |
| --- | --- | --- |
| 交付方 | 产品定位与青年群体服务的匹配度、合规底线、创新性 | 划定五条产品边界，决定合规需求 |
| 主要用户　在校大学生 | 能不能看懂、会不会被说教、填写是否烦琐 | 决定默认画像、三分钟主链路、术语三层解释 |
| 次要用户　职场新人 | 留足刚需之后还剩多少可长期投入 | 决定安全底座优先的分配规则 |
| 演示受众　现场观众 | 几分钟内能否看懂产品与现有工具的差别 | 决定沙盘页的结论层与四张图的排布 |
| 开发团队 | 工期、可维护性、是否有降级方案 | 决定模块优先级划分与项目约束 |

### （二）业务目标

1. 交付目标。提交一个可本地运行、可现场演示、链路完整的产品原型。

2. 产品目标。让收入不确定的人群看见自己消费的机会成本，而不是被劝告少花钱。

3. 叙事目标。说清为什么面向大众的记账与理财工具不适用于这个群体。

### （四）需求收集环节存在的空白

评审认为以下三项在原文档中缺失，补记于此。

1. 未声明一手调研的缺位。产品面向大学生群体，却没有访谈、问卷或可用性测试记录。当前做法是用公开调研数据替代一手调研，这一替代关系必须写明，否则会被质疑判断的依据。

2. 未记录竞品分析。原文档断言现有工具隐含三个不成立的前提，但只给了结论，没有给出具体产品作为对照。

3. 未记录需求优先级的排序依据。建议补一条标准：以缺失后产品是否还能成立为唯一判据。

## 二、可行性分析

### （一）技术可行性

产品的技术实质是规则引擎、蒙特卡洛模拟与图表呈现三者的组合，不涉及模型训练、高并发、分布式计算或实时数据管道。

| 关键技术风险 | 判断 | 约束条件 |
| --- | --- | --- |
| 仿真性能 | 可控。时间步规模在百万量级，向量化实现后的耗时会比性能预算低一到两个数量级 | 实现方式必须是向量化，不能逐路径逐月循环 |
| 反向求解 | 可行。属一维单调搜索，二分法在数十次迭代内收敛 | 必须复用同一批随机路径，否则结果抖动且违反可复现要求 |
| 三层解释生成 | 两条路径均可行。模板可完成三层，接入大模型效果更好 | 必须保留纯规则降级路径，保证离线可用 |
| 界面与图表 | 无技术障碍。四张图表均为标准类型，中文标签通过指定字体解决 | 需要在启动配置中显式指定中文字体 |

技术结论：可行。全产品没有一项技术需要突破现有工具链能力。真正的约束不是能不能做，而是是否在正确的实现路径上。

### （二）经济可行性

| 成本项 | 金额 | 说明 |
| --- | --- | --- |
| 运行环境 | 无 | 本地运行，不使用云服务器 |
| 数据采购 | 无 | 参数全部来自公开报告与行业惯例，不购买原始微数据 |
| 接口费用 | 无 | 不对接行情、交易、征信等付费或需审批的接口 |
| 软件授权 | 无 | 开发语言、数值库、界面框架、绘图库均为开源许可 |
| 模型调用 | 可为零 | 若不接大模型则成本为零；接入则按量计费，演示级用量极低 |
| 报名费用 | 无 | 不产生费用 |
| 人力投入 | 隐性成本 | 不产生现金支出，但决定项目能否按期完成 |

值得指出的是，经济上的零成本并非偶然，而是产品边界设定的直接结果。不做交易、不接行情、不采真实用户数据这三条边界一并消除了金融类产品最常见的数据授权费、交易通道费与安全合规投入。这也意味着，若后续为增强效果而松动任何一条边界，经济可行性需要重新评估。

关键路径为：参数文件 → 仿真引擎 → 账户分配 → 二选一方案 → 界面联调 → 验收自测。其中参数文件与仿真引擎不能滞后，因为下游全部模块依赖仿真输出；二选一方案是路径上唯一没有降级空间的环节。

| 维度 | 结论 | 主要风险 | 缓解手段 |

三维结论一致指向同一个判断：本项目的风险不在能不能做成，而在是否按正确的顺序、沿正确的实现路径做成。

## 四、业务流程

### （一）主流程

主流程共八步，是三分钟演示的动线，与原文档保持一致。

1. 用户选择或填写一份画像，包含基础信息、收入来源、人生目标、悦己预算。

2. 系统校验输入合法性，并实时显示月度可用结余预览。

3. 用户点击推演，系统对收入与支出做多情景仿真。

4. 系统输出每个目标的达成概率与预计达成时间。

5. 系统按价值分层账户规则分配资金，输出四账户分配结果。

6. 系统测算当前风险容量，输出容量等级与权益类建议上限。

7. 系统针对用户最关心的目标给出二选一方案。

8. 用户选择方案后，系统用新预算重新推演，图表即时刷新。

### （二）仿真与决策的内部流程

参数层提供参数与画像，仿真层完成收入建模、支出建模、逐月递推与目标达成计算，决策层在其上完成账户分配、风险容量测算与二选一方案生成，解释层提供术语检索与三层解释，最后统一交由呈现层组织为三页界面。

该流程中存在一处跨层调用：风险容量与二选一方案都需要回读仿真结果，且二选一方案在求解时需要反复触发仿真。原文档规定每层职责单一、不允许跨层调用，此处需要补一条例外说明，否则实现阶段必然与文档冲突。处理方式见系统设计说明书。

### （三）二选一方案的生成流程

这是全产品唯一需要反向求解的流程，也是实现风险最高的一环。

1. 复用当前仿真的随机路径。

2. 计算该目标在当前预算下的按期达成概率。

3. 若当前预算已达标，输出无需压缩的结论。

4. 否则对体验悦己预算做二分搜索，每次搜索复用同一批随机路径重算。

5. 得到可支撑的最大悦己预算，构成方案一，并给出每月需减少的金额。

6. 固定预算不变，检索中位路径的首次达成月份，构成方案二，给出延后月数。

7. 若把预算压到零仍达不到目标线，方案一标记为不可行。

8. 用户点选后重算四项结果并刷新图表。

流程中复用同一批随机路径是关键约束。若每次搜索重新抽样，同一份输入会得到波动的输出，既违反可复现要求，也会让现场演示的结果不可复述。

## 五、需求评审

### （一）总体结论

文档整体质量高于同类学生作品。产品边界以不是什么的方式写死，杜绝了实现阶段的越界；全局规则统一编号并被功能需求显式引用，规则与功能之间可双向追溯；验收标准每条都有可判定标准，可以直接当作自测清单使用；追溯矩阵把痛点、功能需求、模块三者串起来，覆盖度一目了然。

主要问题集中在同一个方向：文档大量给出要做什么，但没有给出做到什么程度。分级阈值、归一化区间、权重、字段结构、错误处理边界，这些决定实现结果的具体数值与结构大面积缺失。若原样进入开发，不同的开发人员会各自按理解补全这些空白，最终对不上。

共识别问题二十项，其中阻断级五项、重要级九项、优化级六项。严重程度定义：阻断级指不修订将导致无法实现或无法验收；重要级指不修订将导致实现结果与预期偏离；优化级指影响文档质量但不影响交付。

### （二）阻断级问题

| 编号 | 问题 | 影响 |
| --- | --- | --- |
| R-01 | 层间数据契约完全缺失 | 五层之间传递什么结构、包含哪些字段、由谁构造，全文未定义，并行开发与单元测试都无从下手 |
| R-02 | 禁止跨层调用与实际实现需求冲突 | 按原文实现会直接违规，按实际需要实现又与文档不符，文档与实现必然分叉 |
| R-03 | 部分参数的来源不可查证 | 附录中若干参数缺少具体机构名与报告名，演示时被追问将无法回答 |
| R-04 | 假设类参数未提供三档取值 | 三档情景对比没有输入 |
| R-05 | 团队规模与项目约束自相矛盾 | 按三人分工写的项目约束在单人推进时全部失效 |

### （五）分维度结论

准确性方面，全局规则与对应功能需求一致，追溯矩阵与模块划分一致，合规要求与产品边界一致。未通过项为：目标数量口径不一致、部分参数来源与实际可查证性不符、个别参数存在但无功能承接。

完整性方面，已覆盖产品定位与边界、系统分层、二十五条功能需求、界面需求、数据需求、非功能需求、约束与假设、十四条验收标准、参数表、数据来源索引、术语表与追溯矩阵。未覆盖需求收集过程、用户故事、业务流程图、可行性分析、层间数据契约、存储设计、接口规范与错误码体系、界面原型、需求变更控制。

可执行性方面，验收标准与性能指标可直接转化为自测清单，参数表已经列全。但数据契约缺失会阻断并行开发，悬空依赖使术语模块无法完整实现，阈值与权重缺失使风险容量模块无法实现，断流处理未定义使达成概率无法确定算法。

结论：文档在做什么的层面可执行，在做到什么程度的层面不可执行。
