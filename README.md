# 青智方舟

面向收入不确定人群的财务仿真与资产配置系统。用户输入收入来源、每月支出与人生目标，系统在三到八年的时间尺度上做多情景现金流仿真，输出四类结论：目标达成概率、预计延后月数、风险容量等级、以及两个互斥的决策方案。

本地运行，全部数据在本机处理。不提供交易功能，不采集个人信息，输出为假设情景下的推演结果，不构成投资建议。

## 快速开始

```bash
pip install -r requirements.txt
python run.py
```

浏览器访问 <http://127.0.0.1:8000>。首次启动会自动建库并导入种子数据。

```bash
python run.py --init-db      # 补建缺失的数据
python run.py --reset-db     # 清空重建
python run.py --port 8080    # 指定端口
```

数据库文件损坏时，程序会把它改名留存再重建，不会在启动阶段崩溃。

## 分层结构

```
frontend/            前端层
  index.html         页面结构。不含任何可见文案
  assets/css/        设计变量与组件样式
  assets/js/         接口客户端、配置目录、格式化、图表
  assets/js/views/   三个页面的渲染逻辑

backend/             后端层
  main.py            启动入口
  config.py          运行期配置（目录、地址、上限、日志），不含业务数据
  common/            错误码
  api/               接口层：路由、请求防护、响应序列化
  services/          应用层：用例编排、画像校验、配置装配
  domain/            领域层：纯计算。仿真、分配、容量、求解
  agents/            智能体：协议、运行时、工具集、生成器
  db/                数据访问层：连接、仓储

database/            数据库层
  schema/            建表脚本，按文件名顺序执行，支持增量演进
  seeds/             业务数据的唯一来源
  var/               运行期库文件（不入版本控制）

docs/                文档
tests/               测试，分 backend、api、data 三组
```

## 数据流

```
浏览器
  │  ① 启动：GET  /api/v1/catalog          取齐枚举、文案、账户、分级、配置与参数
  │  ② 录入：POST /api/v1/profile/preview  结余预览（期望收入口径在服务端）
  │  ③ 推演：POST /api/v1/simulation/run   完整结果
  │  ④ 决策：POST /api/v1/simulation/plan  针对某一目标求解二选一方案
  │  ⑤ 解释：POST /api/v1/terms/explain    术语三层解释
  │  ⑥ 解读：POST /api/v1/agents/<code>/run  任意智能体的统一入口
  ▼
接口层        解析与校验请求、限流、响应头加固；不含业务规则，不接触数据库
  ▼
应用层        装配配置快照、校验画像、编排用例；不直接写 SQL
  ▼
领域层        纯计算。全部系数以参数注入，函数签名里没有业务默认值
  ▼
数据访问层    参数化 SQL，表与字段白名单，写入留痕
  ▼
database/var/qingzhi.db
```

**数据流的硬约束**：任何一条业务数值都从数据库出发，经应用层注入领域层，最终出现在响应里。前端不计算业务量，领域层不读配置文件，接口层不碰数据库。

## 画像与档案

- 内置三份**财务画像**（多元收入型、高刚需型、长期积累型），按收入结构、支出结构、目标时间压力三个财务维度描述，不按生涯路线给人分类。
- 财务画像**不绑定年级**——加载后保留你选择的年级，并按年级重算实习、助研等收入的时间窗口。
- 你可以把当前配置**保存为自己的档案**（本地多份，存于 SQLite），随时加载、删除；内置画像不可删除。

## 智能体

术语解释与结论解读都由智能体承担。定义入库，代码只提供执行引擎。

### 调用流程

一次调用固定为三段，每段都留下一条可追溯的步骤记录：

```
前置工具  →  生成文本  →  合规校验
```

- **前置工具**为生成准备素材：检索语料、提取推演摘要、换算金额与月数。查不到时跳过而不是报错。
- **生成文本**在两条路径中二选一：`rule` 是本地确定性渲染，`openai_compat` 调用 OpenAI 兼容接口。
- **合规校验**是后置步骤，校验不通过时整体失败，绝不把半成品交给调用方。

### 输入输出协议

请求：`{ term, snapshot }`。术语类智能体用 `term`，决策类用 `snapshot`。

响应：

```jsonc
{
  "agent":    { "code", "name", "category", "description" },
  "provider": "rule",          // 实际使用的生成路径
  "degraded": false,           // 外部模型失败并回落到本地时为 true
  "output":   { ... },         // 按该智能体定义的输出结构组织
  "warnings": [],
  "elapsedMs": 8,
  "steps":    [ { "index", "stage", "ref", "title", "status", "detail", "durationMs" } ],
  "disclaimer": { "title", "body" }
}
```

`stage` 取值 `tool` / `generate` / `guard`；`status` 取值 `ok` / `skipped` / `failed` / `replaced`。

### 两条生成路径

| | rule | openai_compat |
| --- | --- | --- |
| 是否联网 | 否 | 是 |
| 结果是否确定 | 是 | 否 |
| 需要配置 | 无 | 服务地址、模型名，凭据从环境变量读取 |
| 失败时 | 不适用 | 自动回到 rule，并在响应中标记降级 |

两道闸门决定走哪条路：全局是否允许联网、以及该智能体是否被指定为本地规则。两道都放行且服务地址与模型名齐备时，才会真正发出网络请求。配置缺失一律报错，不回落代码里的默认值。

**产品不依赖外部模型。** 默认配置下全部走本地规则路径，离线可用；接入模型只是为了在语料基础上把措辞写得更自然。

### 新增一个智能体

只需要改数据：往 `agents` 表加一条定义，往 `agent_bindings` 表绑定已有工具。代码里的工具处理器与本地渲染器都不用动。若绑定了代码中没有实现的处理器，运行期会直接失败——自检接口 `GET /api/v1/agents` 与测试都会暴露出来。

## 数据分层与接口

业务数据分五类，全部可增删改查，写入留痕。

| 类别 | 表 | 接口前缀 |
| --- | --- | --- |
| 字典与配置 | dict_types、dict_items、app_settings、risk_levels、accounts | `/api/v1/catalog` |
| 模型参数与来源 | model_params、data_sources | `/api/v1/catalog/parameters` |
| 文案 | ui_texts、messages | `/api/v1/catalog/ui-texts`、`/api/v1/catalog/messages` |
| 智能体 | agents、agent_tools、agent_bindings | `/api/v1/agents`、`/api/v1/agent-tools` |
| 业务实体 | archetypes 及两张子表、terms 三张表、corpus_documents | `/api/v1/archetypes`、`/api/v1/terms`、`/api/v1/corpus-documents` |

写入示例：

```bash
# 改一个参数，后续推演立即使用新值
curl -X PUT http://127.0.0.1:8000/api/v1/catalog/parameters \
     -H 'Content-Type: application/json' \
     -d '{"key":"sudden_freq","value_base":"2.0"}'

# 打开外部模型（需要同时允许联网并填好地址与模型名）
curl -X PUT http://127.0.0.1:8000/api/v1/catalog/settings \
     -H 'Content-Type: application/json' \
     -d '{"key":"agent.allow_network","value":"1"}'
```

字典表控制着界面行为：收入来源类别在 `dict_items` 的 `attributes` 里声明自己的分布形态与可填字段，新增一类收入来源只需加一条记录，前后端都不需要改代码。

## 核心机制

**收支分离。** 收入流与支出项分开建模：收入流（家庭支持、兼职、奖学金、实习、助研助教）可增删、由年级驱动默认窗口；支出项（房租、餐饮、交通等）逐项配置金额、刚需标记与独立增长率。结余等于收入减支出，而不是一个写死的比例。

**随机路径一次生成、全局复用。** 收入与突发支出矩阵在首次推演时生成并按画像指纹缓存，预算调整只改变支出侧，不重新抽样。这既是性能要求（反向求解要反复评估），也是可复现要求。

**余额递推的向量化。** `b_t = max(0, b_{t-1} + n_t)` 等价于「起点余额加累积和」减去历史最低点，可整体计算而不用逐路径循环。

**达成月份分位不做伪。** 未达成路径视为超出推演范围，因此达成比例低于分位点时返回空值，而不是把未达成记成推演期末——后者会把中位达成月系统性地推到最后一个月。

**方案一求可行上界。** 预算越低储蓄越多、达成概率单调上升，所以「能达标的最小预算」恒等于零。有意义的是反面：在不放弃按期达成的前提下，体验悦己预算最多还能保留多少。二分逼近该上界。

**账户顺序决定谁能分到钱。** 长期复利没有上限，一旦排在体验悦己之前就会吸走全部剩余资金，使体验悦己预算这一输入项完全失效。因此实际顺序是安全底座、成长悦己、体验悦己、长期复利。

**待备额驱动容量下探。** 安全垫厚度扣除了未来到期目标的待备额，待备额在目标到期前线性爬升，刚性目标临近时容量自然下探，目标过后回升。

## 可读性与可追溯

功能跑通不等于用户看得懂。这一组机制是为了回答「凭什么这么算」和「这些数字对我意味着什么」。

**默认进入结论页。** 打开即是三句结论，录入退为定位条上的按钮。系统在开场三十秒内回答「这东西对我有什么用」，而不是要求用户先填完一张空表。

**定位条。** 首屏先说清对谁、做什么、不做什么。产品边界写在最显眼处，把五条硬约束从免责声明变成定位的一部分。

**推演五步。** 折叠在结论之下，用五句白话交代机制：造路径、滚余额、数达成、分四层、定容量。随机性来自抽样，确定性来自入库参数，灵活性来自参数可编辑。

**假设面板。** 每个模型参数陈列取值、性质（实测／假设／惯例）、来源与统计期间，可就地改值并重算。假设类在视觉上明显区分——让用户知道哪些结论不该当真。

**反事实面板。** 把每项参数推到高低两端各跑一遍，按对首要目标达成概率的影响排序。排在最前面的参数就是下一步最该去核实的事。复用同一批随机路径，结果可复现。

**就地解释层。** 结论与图表里的专业词与产品自造词带虚线下划线，点击即在原地展开三层，不跳页、不离开上下文。术语页签降级为全部词条索引备查。解释的价值是即时性——用户看到「容量下探」的那一刻才是提问时刻。

**画像起步。** 录入页顶部可从内置财务画像（多元收入型、高刚需型、长期积累型）中选择一份载入，再逐项改成自己的数；改完可命名保存为「我的档案」，下次直接载入。录入的定位从「填一张表」改为「改一份画像」。

## 设计取舍

**为什么用 SQLite。** 单机单进程、无并发写入、无远程访问，嵌入式数据库足够，且省掉一个需要单独部署的进程。参数需要人工核对来源，因此提供接口而非直接改文件，改动会留痕。

**为什么前端不用框架。** 三个页面、四张图表、一次接口往返即可完成初始化，引入构建工具带来的复杂度高于收益。前端不承担任何业务计算。

**为什么前端不出现文案。** 页面里只有 `data-text` 占位键，所有可见文字、枚举选项、配色、图表标题都由接口下发。这样改文案不需要动代码，也使得「前端不含业务数据」成为可以自动检查的约束。

**为什么术语解释要走智能体。** 术语接口与智能体接口共用同一条链路，就不会出现两个入口结果不一致的情况。同时智能体的步骤轨迹让「这段话是怎么来的」变得可追溯。

## 边界与已知限制

1. 术语语料是按公开披露制度与现行制度的要素整理的要点，不是某一产品的原文，也不逐字引用条文。若需要引用具体产品，应替换为该产品的官方文件并登记来源与获取日期。
2. 参数表中若干条目的来源描述只到报告名称，未到年份、样本量与可引用位置。
3. 目标达成以全部储蓄余额为口径，未区分安全底座与长期复利。
4. 账户分配顺序与需求原文的表述不同，理由见上文「账户顺序决定谁能分到钱」。
5. 外部模型路径默认关闭。开启后需要自行准备服务端点与凭据，凭据只从环境变量读取。

## 检查与测试

```bash
python -m pytest          # 单元、接口与数据一致性
python -m ruff check .    # 静态分析
node --check frontend/assets/js/main.js
```

`tests/data/` 下有一组静态检查，是「业务数据只来自数据库」的守门人：

- 扫描后端与前端代码，把种子文件里的业务取值逐个拿去搜索，任何一处出现都判为硬编码；
- 校验前端引用的每个文案键、字典类型、配置键、参数键在数据库中真实存在；
- 反向校验每条界面文案与提示文案都被某处引用，避免留下死文案；
- 校验配置项都有代码消费、领域层不碰数据库与文件、接口层不出现 SQL、页面不含可见文案。
