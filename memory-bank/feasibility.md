# 可行性分析

> **阅读提示**：本文件是需求阶段的前瞻判断，工作量估算以需求文档给定的分工为前提。实现最终按单人路径完成，实际取舍与结果见 progress.md 与 decisions.md。文末的时间结论「三人可行、单人偏紧」已被事实覆盖。

## 一、分析范围

原需求规格说明书未单独设置可行性分析章节，仅在附录与约束中零散提及技术前提。本文按技术、经济、时间三个维度补齐，每个维度给出结论与依据，并列明不成立的假设。

分析以"三名开发人员、交付周期内完成可演示作品"为基准场景，同时给出单人开发场景下的差异结论。

## 二、技术可行性

### （一）技术实质

产品的技术实质是规则引擎、蒙特卡洛模拟与图表呈现三者的组合，不涉及模型训练、高并发、分布式计算或实时数据管道。这一判断决定了整体的技术难度上限。

按模块拆解，技术难度分布如下：

| 模块 | 技术实质 | 难度 | 关键风险 |
| --- | --- | --- | --- |
| M1 目标与收入录入 | 表单、校验、状态管理 | 低 | 无 |
| M2 现金流仿真沙盘 | 随机过程建模、蒙特卡洛抽样、分位数统计 | 中 | 向量化程度不足会导致性能不达标 |
| M3 价值分层账户 | 带优先级的顺序分配与缺口结转 | 中 | 分配守恒的边界情形 |
| M4 动态风险容量评估 | 指标归一化、加权合成、分档规则 | 中 | 归一化区间的选取缺依据 |
| M5 多目标动态优化 | 反向求解，嵌套搜索 | 高 | 搜索次数与随机路径复用的矛盾 |
| M6 金融术语三层拆解 | 语料检索、受约束文本生成 | 中 | 第三层的生成质量与降级路径 |
| M7 成长护照 | 规则判定与记录 | 低 | 无 |
| M8 典型画像案例库 | 内容组织 | 低 | 无 |
| 界面与图表 | 三 Tab 布局、四张标准图表 | 中 | 中文标签与响应式 |

### （二）关键技术风险的可行性判断

**1. 仿真性能。** 默认参数为一万条路径、九十六个月，时间步规模在百万量级。若采用逐路径、逐月的解释型循环，耗时可能逼近性能预算；若将整批路径一次性组织为二维数组并按月向量化递推，实测耗时会比预算低一到两个数量级。结论是性能可控，但**实现方式必须是向量化**，这一点需要在设计阶段就定下来，后期改造成本很高。

**2. 反向求解。** M5 需要回答"预算压到多少才能按期达成"，属于对目标函数单调性可依赖的一维搜索问题，二分法在数十次迭代内即可收敛。风险不在于算法本身，而在于每次迭代都要触发一次完整仿真。缓解手段有两条：一是复用同一批随机路径，使两次评估之间的差异只来自预算变化而非抽样噪声；二是把搜索空间限制在预算上限区间内，避免无效迭代。结论是**技术上可行，但必须复用随机路径**，否则同时违反性能预算与可复现要求。

**3. 三层解释的生成。** 第一层与第二层可由模板与语料片段拼装完成，不存在技术障碍。第三层要求把风险换算成"该用户某个目标延后多少个月"，模板同样可以实现，只是措辞较为固定。若引入大模型，效果更好，但需保留降级路径。结论是**两条路径均可行**，即使不接入任何外部模型，产品仍然完整。

**4. 界面与图表。** 三 Tab 布局与四张图表（分位带、达成概率、堆叠面积、容量日历）均属标准图表类型，所选界面框架与绘图库可以直接实现，中文标签通过显式指定字体解决。结论是**无技术障碍**。

### （三）技术可行性结论

可行。全产品没有一项技术需要突破现有工具链能力，最高难度的 M5 也只要求实现一次一维搜索。**真正的技术约束不是"能不能做"，而是"是否在正确的实现路径上"**——向量化与随机路径复用这两项若在早期决定错误，后期返工代价显著。

## 三、经济可行性

### （一）成本结构

| 成本项 | 金额 | 说明 |
| --- | --- | --- |
| 运行环境 | 无 | 本地运行，不使用云服务器 |
| 数据采购 | 无 | 全部参数来自公开报告与行业惯例，不购买原始微数据 |
| 接口费用 | 无 | 不对接行情、交易、征信等任何付费或需审批的接口 |
| 软件授权 | 无 | 开发语言、数值库、界面框架、绘图库均为开源许可 |
| 模型调用 | 可为零 | M6 若不接大模型则成本为零；接入则按量计费，演示级用量极低 |
| 报名费用 | 无 | 不产生费用 |
| 人力投入 | 隐性成本 | 不产生现金支出，但决定项目能否按期完成 |

### （二）成本结构与产品边界的耦合

值得指出的是，**经济上的零成本并非偶然，而是产品边界设定的直接结果**。原文档 2.3 节明确不做交易、不接行情、不采真实用户数据，7.5 节明确不采集不上传个人信息、不设登录鉴权——这几条边界一并消除了金融类产品中最常见的三项成本来源：行情数据授权费、交易通道费、以及伴随用户数据而来的安全合规投入。

这也意味着：**若后续为增强效果而松动任何一条边界，经济可行性需要重新评估**。例如为了做真实产品对比而接入在售产品行情，就会立刻引入数据授权成本。

### （三）经济可行性结论

可行，且现金成本接近于零。主要成本是人力时间而非资金，因此风险重心应放在时间维度而非资金维度。

## 四、时间可行性

### （一）工作量分解

按相对工作量给出估算，单位为理想人日，不含沟通与返工。实际投入通常为估算的一点五至两倍。

| 工作包 | 三人团队人日 | 单人人日 | 说明 |
| --- | --- | --- | --- |
| 参数文件与语料收集 | 三至五 | 三至五 | 纯人工考据，无法并行摊薄 |
| M1 录入与校验 | 二至三 | 二至三 | 表单为主 |
| M2 仿真引擎 | 四至六 | 四至六 | 向量化设计与验证 |
| M3 账户分配 | 二至三 | 二至三 | 规则实现 |
| M4 风险容量（含容量日历） | 三至四 | 三至四 | 分级规则与逐月重算 |
| M5 缺口与二选一 | 五至八 | 五至八 | 反向求解与性能调优 |
| M6 术语三层 | 四至六 | 四至六 | 含降级路径 |
| 界面与四张图表 | 五至七 | 五至七 | 三 Tab 与图表联动 |
| 联调与验收自测 | 四至六 | 四至六 | 十四条验收项 |
| 演示材料与三套预案 | 三至四 | 五至八 | 单人要兼顾出镜与讲解 |
| 合计 | 三十五至五十二 | 三十八至五十八 | — |

### （二）关键路径

主线依赖关系为：参数文件 → 仿真引擎 → 账户分配 → 二选一方案 → 界面联调 → 验收自测。

其中**参数文件与仿真引擎**不能滞后，因为下游全部模块都依赖仿真输出；**M5 是路径上唯一没有降级空间的环节**，它既不能砍掉（属核心模块），也不能先做简化版再补齐（简化版无法满足"必须给出具体数字"的验收要求）。相比之下，M4 的容量日历、M6 的大模型路径、M7、M8 均可降级或舍弃。

### （三）时间可行性结论

三人团队可行，但排期紧凑，前提是严格执行 8.4 节"非核心模块预留降级方案"的要求。

**单人场景下结论需要调整**：技术工作量可以承担，但"演示材料与三套预案"这一项在单人场景下工作量显著上升，因为原本由队长承担的叙事与出镜工作无法分摊。建议单人开发时采用如下顺序：先打通 M1 至 M3 与 M5 的主链路并完成一次可演示的完整流程，再回补 M4 与 M6，最后集中投入演示材料。**先有能演的东西，再谈完整性。**

## 五、三维交叉结论

| 维度 | 结论 | 主要风险 | 缓解手段 |
| --- | --- | --- | --- |
| 技术 | 可行 | 实现路径选择错误（未向量化、未复用随机路径） | 在设计阶段固定两条实现约束，写进接口契约 |
| 经济 | 可行，现金成本接近于零 | 后续松动产品边界会引入数据与合规成本 | 把五条产品边界视为不可协商项 |
| 时间 | 三人可行，单人偏紧 | M5 无降级空间，演示材料在单人场景下负担加重 | 主链路优先，非核心模块预先规划降级形态 |

三维结论一致指向同一个判断：**本项目的风险不在"能不能做成"，而在"是否按正确的顺序、沿正确的实现路径做成"**。
