# 数据设计

> 本文件为当前落地的数据设计。设计阶段的初版方案（纯文件存储、十三类逻辑实体）已在实现阶段推翻，判断依据保留在下述选型一节与 decisions.md 的 D-14 中。

## 一、存储方案

### （一）需求文档的原始约定

原文档 6.1 节给出的存储位置是"本地参数文件""本地，可导出为文件""本地目录""本地画像库"，运行数据"内存，不落盘"。也即原设计不含数据库，全部以文件形式存储。

### （二）实现阶段的结论

**以 SQLite 为唯一运行期数据源，纯文件退化为导入用的种子文件。**

推翻原设计的关键理由不是技术指标，而是约束层面的变化：产品要求所有业务数据必须来自数据库、由接口提供增删改查，枚举与字典类固定数据同样入库。这一条本身即排除了以文件为运行期数据源的可能。

原设计中被否掉的两条依据需要更正：

- 「参数需要人写人手，所以要用纯文本文件」——人工核对的必要性保留，编辑入口从表格软件改为接口。来源与性质成为强制填写的字段，比自由编辑更能保证参数表的完整性，代价是核对时的便利性下降。这是明确接受的取舍。
- 「数据量极小，文件读取耗时可忽略」——仍成立，但已不构成选型依据。选择嵌入式数据库的收益在于约束能力、查询能力与写入留痕，而非性能。

「运行数据不落盘」这一条仍然保留：仿真结果只存在于内存与响应体中，不写库。需要区分的是两类画像——内置画像是构造的演示数据，长期驻留数据库；用户在自己浏览器里填写的画像只随请求体上行，不落盘。

## 二、数据分类与生命周期

| 数据类别 | 来源 | 存储位置 | 生命周期 | 是否入库 |
| --- | --- | --- | --- | --- |
| 模型参数 | 公开调研数据与行业惯例 | model_params、data_sources | 长期，随版本修订 | 是 |
| 字典与配置 | 产品约定 | dict_types、dict_items、app_settings、risk_levels、accounts | 长期 | 是 |
| 典型画像 | 基于公开数据构造 | archetypes 及三张子表 | 长期 | 是 |
| 术语与语料 | 公开在售产品官方文件 | terms、term_aliases、term_sources、corpus_documents | 长期 | 是 |
| 界面文案与提示 | 产品约定 | ui_texts、messages | 长期 | 是 |
| 智能体定义 | 产品约定 | agents、agent_tools、agent_bindings | 长期 | 是 |
| 用户画像 | 用户填写 | 随请求体传输，不落盘 | 单次请求 | 否 |
| 仿真运行数据 | 系统生成 | 内存 | 单次推演 | 否 |
| 配置变更记录 | 系统生成 | change_log | 长期 | 是 |

## 三、库表清单

共二十一张表，按用途分六组。建表脚本在 database/schema 下按版本递增，结构变更以追加脚本的方式演进，不修改已发布的脚本。

| 组别 | 表 | 用途 |
| --- | --- | --- |
| 字典 | dict_types、dict_items | 年级、收入来源类别、支出类别、风险偏好等枚举。条目自带 attributes，声明分布形态、可填字段与默认值 |
| 配置 | app_settings、risk_levels、accounts | 引擎阈值与权重、风险容量分级与权益上限、四账户定义与分配优先级 |
| 参数与来源 | model_params、data_sources | 带来源与性质的业务参数，及其来源登记 |
| 文案 | ui_texts、messages | 界面全部可见文案与提示文案。前端不写死任何一句 |
| 业务实体 | archetypes、archetype_income_sources、archetype_expenses、archetype_goals、terms、term_aliases、term_sources、corpus_documents | 画像及其收支与目标、术语与其别名与来源、语料文档 |
| 智能体 | agents、agent_tools、agent_bindings | 智能体定义、工具定义、两者的绑定关系 |
| 审计 | change_log | 写入留痕。只记表名与主键，不记用户画像内容 |

字典项的 attributes 承担了可扩展性：一类收入来源在字典里声明自己的分布形态与可填字段，新增一类收入来源只需加一条记录，前后端都不改代码。

## 四、关键实体的字段

### （一）画像

| 字段 | 约束 | 说明 |
| --- | --- | --- |
| archetype_id | 主键 | 画像标识 |
| kind | builtin 或 user | 内置画像不可删除，用户档案可增删改 |
| city | 非空，已废弃 | 城市变量移除后不再读写，仅为兼容旧库保留，写入时补空串 |
| grade | 非空 | 年级，仅作推演兜底值，不覆盖用户当前选择 |
| living_cost | 大于零 | 家庭支持。默认取参数表的全国月均生活费 |
| living_growth | 零至零点一 | 家庭支持年增长率 |
| initial_balance | 非负 | 现有积蓄，作为仿真的初始余额 |
| risk_appetite | 字典枚举 | 风险偏好档位 |
| months、paths、seed | 整数 | 推演时长、仿真次数、随机种子，上下界来自配置 |
| growth_budget、treat_budget | 非负 | 成长悦己与体验悦己的月度上限 |

### （二）收入来源

| 字段 | 说明 |
| --- | --- |
| source_type | 对应收入来源字典的 code |
| enabled | 启用开关。固定型收入恒为启用 |
| probability | 参与概率。必须允许取零，即完全不发生 |
| amount_low、amount_mid、amount_high | 金额区间，须满足下限不大于中值、中值不大于上限 |
| start_month、end_month | 时间窗口，由年级驱动默认值 |
| interrupt_prob | 中断概率。是否可用由字典项声明 |

### （三）支出项

| 字段 | 说明 |
| --- | --- |
| category | 对应支出类别字典的 code |
| amount | 月金额 |
| essential | 是否刚需。刚需不可压缩，用于安全垫与应急金测算 |
| growth_rate | 独立年增长率 |
| enabled | 启用开关 |

结余等于收入减支出，逐月模拟。支出项是「每月花掉的钱」，悦己预算是「存起来的储备」，两者不混淆。

### （四）目标

| 字段 | 说明 |
| --- | --- |
| goal_id | 画像内唯一 |
| name、amount | 名称与金额，金额必须大于零 |
| due_month | 到期月份，须落在推演范围内 |
| priority | 越小越优先，决定缺口计算与方案求解的顺序 |

### （五）账户

accounts 表定义四账户的 code、名称、配色与 priority。priority 是分配的唯一依据，改动它等同于改动分配语义，当前顺序为安全底座、成长悦己、体验悦己、长期复利（见 decisions.md 的 D-19）。

### （六）参数

model_params 表逐条登记参数的基准值、三档取值、单位、来源、时期与性质。性质取实测、假设、惯例三者之一，假设与惯例类必须给出三档取值，否则情景对比没有输入。

## 五、种子文件与导入

database/seeds 下十五份 JSON 是业务数据的唯一来源，与建表脚本一一对应：accounts、agents、agent_bindings、agent_tools、app_settings、archetypes、corpus_documents、data_sources、dict_items、dict_types、messages、model_params、risk_levels、terms、ui_texts。

首次启动自动建库并导入，库文件在 database/var 下，不入版本控制。库文件损坏时改名留存后重建。改数据的正规入口是接口，每次写入落 change_log。

## 六、数据校验规则

### （一）字段级

| 规则 | 适用字段 |
| --- | --- |
| 概率与比率类字段取值落在零至一之间 | probability、interrupt_prob、hit_probability、equity_cap、final_cap |
| 金额类字段非负 | 收入金额区间、支出金额、目标金额、账户分配额与余额 |
| 月序类字段为正整数且不超出推演时长 | due_month、start_month、end_month |
| 整数类字段不接受浮点 | months、paths、seed、due_month |
| 枚举类字段只能取字典中已定义的 code | grade、city、risk_appetite、source_type、category |
| 三个取值须满足递增关系 | amount_low ≤ amount_mid ≤ amount_high |

整数类字段对浮点入参不静默截断，而是明确要求整数并给出中文提示——静默截断会让使用者以为自己填的数字生效了。

### （二）实体级

| 规则 | 依据 |
| --- | --- |
| 目标数量不少于一、不多于配置上限 | 6.3 节 |
| 启用的收入来源不超过配置上限 | 6.3 节 |
| 仿真次数与推演时长的乘积不超过配置上限 | 防止单个请求把内存推到不可控 |
| 内置画像不可删除 | decisions.md 的 D-21 |

### （三）跨实体级

| 规则 | 依据 |
| --- | --- |
| 账户分配守恒：同月四账户分配额之和等于当月可用资金 | AC-03 |
| 分配优先级：安全底座未填满时，体验悦己与长期复利的当月分配为零 | AC-04 |
| 结果完整性：每条目标都有对应的达成结果，概率落在零至一之间 | AC-02 |
| 可复现性：同画像同种子两次运行的达成概率一致 | AC-13 |
| 达成月份分位取全样本分位，达成比例不足相应分位点时为空值 | GR-07 |
| 断流路径计入分母并按未达成处理 | 评审问题 R-12 |

校验失败时给出中文提示并指明具体字段，程序不得崩溃。错误分类与错误码见接口契约文档。

## 七、一致性检查

测试中的 test_data_integrity.py 承担两类守门：

1. 扫描后端与前端代码，把种子文件里有辨识度的业务取值逐个拿去搜索，任何一处出现都判为硬编码。
2. 校验前端引用的每个文案键、字典类型、配置键、参数键在数据库里真实存在；反向再检查每条界面文案与提示文案都被某处引用，避免死文案复发。
