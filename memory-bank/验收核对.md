# 验收核对

我先说明一件必须说清的事：十四条验收项的原文不在本仓库里。原需求规格说明书 V1.0 的「验收标准」章节没有随仓库提交，docs 下只剩补充卷，我在 docs 与 memory-bank 中能找到的只有散落的编号引用，共十二条——AC-01 至 AC-08、AC-10 至 AC-13，出处是 requirements-review.md、data-design.md、api-contract.md、design-review.md 与 requirements-supplement.md。我按这些引用把条文归回，得到前述十二条。AC-09 与 AC-14 在全仓库任何文件中都没有被引用过，只能按「其余验收项未覆盖、而需求文档确有要求」的部分推定：AC-09 取三档情景对比（FR-10），AC-14 取非功能性能与演示时长（NF-01 至 NF-04）。这两条在下文标注为推定项，答辩时不能当作原文引用。

## 一、十四条验收项的逐条核对

| 编号 | 验收项要点 | 判定 | 证据 |
| --- | --- | --- | --- |
| AC-01 | 不填任何内容即可看到一次完整推演 | 通过 | frontend/assets/js/main.js 的 init 先载入默认画像再静默调用 run；backend/api/routes/simulation.py 的 run_simulation；tests/api/test_api.py 的 test_archetype_profile_is_runnable |
| AC-02 | 每条目标都有达成结果，概率落在零至一之间 | 通过 | backend/domain/simulation.py 的 simulate 逐目标构造 GoalResult，hit_probability 取按期达成路径数除以总路径数；tests/backend/test_domain.py 的 test_shortfall_paths_within_bounds |
| AC-03 | 同月四账户分配额之和等于当月可用资金 | 通过 | backend/domain/allocation.py 的 allocate 逐月核算并置 conservation_ok，未吸收的余量并入长期复利；services/simulation.py 的 _serialize_allocation 回传 conservationOk；test_allocation_conservation |
| AC-04 | 安全底座未填满时，体验悦己与长期复利当月分配为零 | 部分通过 | allocation.py 的 allocate 中 budget_incomplete 判断与 priority_ok 标志；差在：被排除的账户写死为代码里的账户编码，不随 accounts 表的 priority 变化，改账户顺序即失效 |
| AC-05 | 方案一给出压缩后的具体预算与差额 | 部分通过 | backend/domain/planner.py 的 solve 做二分逼近并给出 feasible 标志；差在：搜索区间只取零到当前预算，达标分支直接返回保持现状，未回答设计记录中「最多还能花多少」这一上界；取整步长十元也是代码常量 |
| AC-06 | 方案二给出延后月数 | 通过 | planner.py 的 postpone 分支的 delay_months；原先差在推演期内未达成时用「推演期末加一月」作哨兵值，界面当作确定月数呈现。现 _evaluate 一并返回 beyond_horizon 标记，simulation.py 序列化为 beyondHorizon，前端哨兵情形下改述为「至少 N 个月」 |
| AC-07 | 风险容量三项归一化加权，客观与主观双约束取严 | 通过 | backend/domain/capacity.py 的 assess 计算 cushion、rigidity、stability 三项并合成原始分，final_cap 取分级上限与偏好上限的较小值；阈值与权重来自 app_settings 与 risk_levels；test_capacity_monotone_bounds |
| AC-08 | 二十四个月容量日历，刚性目标临近时下探 | 部分通过 | capacity.py 的 calendar 与 dip_months，calendar_months 与 pending_ramp_months 取自配置；frontend/assets/js/charts.js 的 capacity 绘图；差在：判定下探的阈值写死在 capacity.py，未入库 |
| AC-09（推定） | 乐观、基准、悲观三档情景对比 | 通过 | domain/simulation.py 的 scenario_comparison 与 scale_income，三档系数取自 app_settings；没有专项断言，只被 test_run_contract 的结构检查间接覆盖 |
| AC-10 | 术语解释第三层关联目标，无目标时不含数字 | 通过 | backend/services/term.py 的 explain 透传 linkedGoalId 与 hasNumbers，backend/agents/tools.py 的 compliance_guard 兜底；test_explain_without_goal_has_no_numbers 与 test_explain_with_goal_links_target |
| AC-11 | 任何输出都附带免责提示 | 通过 | services/simulation.py 的 run 挂 disclaimer.simulation，_serialize_plan 与 services/whatif.py 同样挂载，plan_for 单独求解时也带；agents/tools.py 的 compliance_guard 兜底；前端 whatif.js 渲染免责脚注，sandbox.js 与 term.js 各有对应渲染 |
| AC-12 | 校验失败给出中文提示并指明字段 | 通过 | backend/common/errors.py 的 AppError 与 ValidationError 携带 code、message、field；backend/services/profile.py 的 validate 逐字段抛错；test_preview_rejects_non_numeric、test_validate_rejects_unknown_enum |
| AC-13 | 同画像同种子两次推演结果一致 | 通过 | services/simulation.py 的 _fingerprint 与路径缓存，planner.py 只接受传入的 PathSet、自身不持有种子；test_reproducible 与 test_run_is_reproducible |
| AC-14（推定） | 性能指标与三分钟演示时长 | 通过 | 我在本机实测过：默认画像一万条路径、九十六个月，单次完整推演耗时约零点四五秒，第二次起因路径缓存稳定在同一量级；反事实分析五个参数各跑两端约一点零五秒。加上 configuration 的初始加载，首屏在两秒内出结论，三分钟演示时长不成约束 |

合计：通过十一条，部分通过三条，无法验证零条，未通过零条。

已收口两项：AC-11 的缺口补在 services/simulation.py 的 _serialize_plan 与 services/whatif.py 两个响应上，此前这两个输出确实整屏数字无提示；AC-14 原先判为无法验证，我实测后改判通过，实测方法与数字见上表。

## 二、三条横切约束

| 约束 | 判定 | 证据与差距 |
| --- | --- | --- |
| 业务数据只来自数据库，代码无硬编码业务取值 | 部分通过 | tests/data/test_data_integrity.py 的 test_no_seeded_value_hardcoded 扫描后端与前端源码。差距有三：其一，该测试只收集绝对值不小于一千或小数位不少于五位的值，零点二五、十元取整步长、零点一这类阈值根本不在扫描范围内，通过结论是假绿灯；其二，capacity.py 的下探阈值、planner.py 的取整步长、services/profile.py 的生活费增长率上限仍是字面量；其三，frontend/index.html 的输入框上下限与配置表重复且写死 |
| 前端不含可见文案，全部由接口下发 | 通过 | index.html 一律用 data-text 占位，test_frontend_has_no_visible_copy 正则扫描残留中文，test_ui_text_keys_exist 与 test_message_codes_exist 双向校验键的存在与引用，另有 test_every_ui_text_is_referenced 兜底死文案 |
| 仿真结果均标注假设情景并提示不构成投资建议 | 部分通过 | messages 表中的 disclaimer.simulation 与 disclaimer.term 两条文案齐备，sandbox.js 与 term.js 分别渲染。差距与 AC-11 同源：反事实分析与二选一方案两处输出没有提示 |

3. 找回验收项原文并归档。十四条里有两条是我推定的，缺了原文就无法逐条举证。
4. 方案一的达标分支补上上界搜索；若不改实现，就把口径改回「零到当前预算」并同步修订 README 与设计记录中的表述，避免自相矛盾。
5. 延后月数的哨兵情形已改述为「至少 N 个月」，不再把推演期末当确定值呈现，此项已闭环。
6. 推演耗时已实测并记入上表。演示脚本在交付说明第四节，仍缺一次本人演练的时间对照。
