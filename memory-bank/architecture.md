# 架构设计

> 本文件为当前落地架构。设计阶段的初版方案（五层分层、纯文件存储、声明式界面框架）已在实现阶段全部推翻，其结论保留在 decisions.md 的 D-08、D-09、D-13、D-14 四条中，此处不再重复。

## 一、架构选型

### （一）选型结论

**分层单体，单机单进程，浏览器访问本机回环端口。目录按前端、后端、数据库、文档四层组织，后端内部再分接口、应用、领域、数据访问四层。**

不是微服务，不是无服务架构，也不是桌面原生应用。这个结论由产品形态直接决定：交付形态是可本地运行的交互原型，数据全部本地处理不上传，不设登录鉴权，不依赖付费或需审批的外部接口。这些条件叠加起来，一个进程加一个浏览器页面就是完整的系统边界。

界面是原生 HTML 与 JavaScript，由 Flask 提供接口。它与"前后端分离"的区别在于不引入前端工程化：没有构建工具、没有框架、没有状态管理库。

### （二）为什么不做微服务

| 维度 | 微服务的适用条件 | 本项目的实际情况 |
| --- | --- | --- |
| 部署规模 | 需要独立扩缩容的服务群 | 单机运行，无扩缩容需求 |
| 团队规模 | 多团队各自负责一个服务 | 单人开发，拆分只增加沟通成本 |
| 调用开销 | 服务间网络调用可接受 | 全部计算在一台机器内，跨进程调用纯属浪费 |
| 运维成本 | 有专门的运维支撑 | 无，且交付周期内不允许引入 |
| 数据边界 | 各服务拥有独立数据 | 全部数据在一份嵌入式数据库里，拆不开 |

结论：微服务在本项目里不解决任何真实问题，只会把一次函数调用变成一次序列化加进程间通信。

### （三）为什么不引入前端工程化

需求文档要求界面采用轻量框架。引入构建工具会立即带来工具链维护、产物打包与联调排错三项成本，而这些成本换不来任何产品收益：页面只有三个页签，图表只有四张且类型固定，交互只有悬停提示。

不引入框架不等于放弃接口边界。恰恰相反，采用原生前端之后，前后端之间是一条真实的 HTTP 契约，可以用静态检查守住"前端不承载业务计算、不含可见文案、不含业务取值"这三条约束——这正是数据一致性检查所做的事。

## 二、设计理念

现有面向大众的理财与记账工具，其产品设计隐含三个前提：收入确定、目标单一、投入固定。本项目的基础判断是，这三个前提在 Z 世代群体身上全部不成立。

| 隐含前提 | 现实情况 | 带来的后果 |
| --- | --- | --- |
| 收入确定 | 收入由家庭支持、兼职、奖学金、实习、助研助教拼合而成，随年级、学期、就业市场波动 | 按常量计算的工具必然失真 |
| 目标单一 | 升学、考证、求职备付金、旅行、置业储备往往同时存在 | 单目标工具无法处理资源竞争 |
| 投入固定 | 突发支出与情绪消费随时可能打断储蓄计划 | 刚性预算一旦破窗即被弃用 |

## 三、目录与分层

```text
frontend/            前端层：页面结构、设计变量、脚本与视图
  index.html         只描述结构，不含任何可见文案
  assets/css/        tokens.css 设计变量，app.css 组件样式
  assets/js/         api 客户端、配置目录、格式化、图表
  assets/js/views/   三个页面的渲染逻辑

backend/             后端层
  main.py            启动入口
  config.py          运行期配置。按设计不含任何业务数据
  common/            错误码
  api/               接口层：路由、请求防护、响应序列化
  api/routes/        目录、画像、推演、方案、术语、智能体六组路由
  services/          应用层：配置装配、画像校验、用例编排
  domain/            领域层：纯计算。仿真、分配、容量、求解、解释
  agents/            智能体层：运行时、注册表、工具、生成器
  db/                数据访问层：连接、建库、仓储

database/            数据库层
  schema/            建表与索引，按版本递增
  seeds/             业务数据的唯一来源，十五份种子文件
  var/               运行期库文件，不入版本控制

docs/                文档。赛事背景集中在 交付说明.md
memory-bank/         工程记忆
tests/               测试，按 backend、api、data 三组
```

后端四层各自守住的东西：

| 层次 | 不得出现的事物 | 由什么守住 |
| --- | --- | --- |
| 前端 | 业务计算、可见文案、业务取值 | 数据一致性检查扫描页面与脚本 |
| 接口层 | SQL、业务规则 | 扫描接口层是否出现写库语句 |
| 智能体层 | 网络凭据、业务默认值 | 凭据只从环境变量读取，配置缺失即报错 |
| 领域层 | 数据库、文件、网络、业务默认值 | 扫描领域层是否出现数据库连接、文件读写与网络库 |
| 数据访问层 | 未经白名单的表名与字段名 | 白名单常量，接口层不出现 SQL |

## 四、主流程

1. 用户选择一份内置画像，或自己填写收支与目标。
2. 前端调用结余预览，实时显示月度可用结余。
3. 用户点击推演，后端对收入与支出做多情景仿真。
4. 返回每个目标的达成概率与预计达成时间。
5. 返回按价值分层账户规则的资金分配结果。
6. 返回当前风险容量等级与权益类建议上限。
7. 返回针对首要目标的二选一方案。
8. 用户点选方案后，前端带上新预算重新推演，图表即时刷新。

## 五、数据流与配置装配

调用方向自上而下，逐层收敛职责：

```text
浏览器
  │ ① 取配置目录  ② 结余预览  ③ 推演  ④ 求解方案  ⑤ 术语解释
  ▼
接口层（backend/api）
  │ 解析与校验请求、主机校验、请求体上限、重计算互斥、响应头加固
  │ 不含业务规则，不接触数据库
  ▼
应用层（backend/services）
  │ 从数据库装配配置快照、校验画像、编排用例、序列化响应
  ▼
智能体层（backend/agents）
  │ 前置工具 → 生成文本 → 合规校验
  ▼
领域层（backend/domain）
  │ 纯计算。全部系数以 DomainConfig 注入，函数签名里没有业务默认值
  │ 不读文件、不连数据库、不发网络请求
  ▼
数据访问层（backend/db/repository）
  │ 参数化 SQL，表与字段走白名单，写入留痕
  ▼
database/var/
```

配置装配：启动时由应用层一次性把数据库里的字典项、配置项、账户定义、风险分级、模型参数读出来，合成 DomainConfig 后注入领域层。之后任何一次配置写入都会让快照失效，下一次读取时重建，因此改参数立刻生效，不需要重启。

参数表与配置表的分工：带来源与性质的业务参数只放参数表，引擎的阈值、权重、归一化区间只放配置表。同一项配置写进两张表会导致改一处不生效。

## 六、全局设计规则

| 编号 | 规则内容 | 适用范围 |
| --- | --- | --- |
| GR-01 | 账户分配优先级固定为：安全底座 → 成长悦己 → 体验悦己 → 长期复利 | M3、M5 |
| GR-02 | 最终建议配置取风险偏好允许值与风险容量允许值的较小者 | M4 |
| GR-03 | 账户余额不允许为负，出现缺口时记为断流事件并回写提示 | M2、M5 |
| GR-04 | 所有仿真结果必须标注为假设情景，附带不构成投资建议的提示 | 全部模块 |
| GR-05 | 术语解释的第三层必须关联用户已设置的具体目标，无目标时输出固定合规文案，不得生成数字 | M6 |
| GR-06 | 悦己预算超支不阻断流程，但需记录超支额并回写后果 | M3、M5 |
| GR-07 | 随机种子可配置且默认固定，保证结果可复现 | M2 |
| GR-08 | 所有数据本地处理，不得上传外部服务器 | 全部模块 |
| GR-09 | 假设类参数必须在结果说明中标注其假设性质 | 参数层 |
| GR-10 | 演示时表述为原型已跑通，落地时表述为接入方案，两者不得交叉 | 呈现层、演示 |

GR-01 的顺序与需求文档原文不同，理由见 decisions.md 的 D-15 与 D-19。

## 七、跨层调用的两条例外

分层要求"职责单一、不得跨层调用"，实际存在两处必要的例外，此处补齐条款。

### （一）M5 需要重复调用仿真层

二选一方案属于反向求解：给定目标的达成期限，反推还能花多少体验悦己预算。这不是一次仿真能得出结果的，需要对预算做搜索，每次搜索都重新评估达成概率。

处理方式：决策层通过一个受控的求解入口重复调用仿真层，并约定三条约束。

1. 搜索过程中的每一次评估**必须复用同一批随机路径**。若每次搜索重新抽样，结果会因随机性而抖动，同时违反 GR-07 的可复现要求。
2. 求解必须设定迭代上限与无解判断，避免在极端参数下无限迭代。
3. 求解目标线取中位路径能够按期达成。

### （二）M4 的容量日历需要逐月重算

容量日历要求输出未来若干个月的容量等级序列，每月都要用当期安全垫厚度重新分级，等同于对仿真结果做一次按月切片的二次计算。

处理方式：这部分计算在仿真阶段一次算好并缓存为独立的日历结构，前端只负责绘制，不在渲染时重算。切换图表的交互频率远高于重算频率，把计算压在渲染路径上会直接影响界面响应。

## 八、智能体层

### （一）位置与职责

智能体层位于应用层之下、领域层之上。它不替代领域层——领域层仍然负责计算，智能体负责把计算结果转成人能读懂的话，以及把这句话的来源与校验过程留下来。

```
应用层（services/agent.py）
  │ 清洗输入、装配上下文、序列化输出
  ▼
智能体层（agents/）
  │ runtime.py     编排：前置工具 → 生成 → 后置校验
  │ registry.py    从数据库读智能体定义与工具绑定
  │ tools.py       工具处理器，写入共享区
  │ providers.py   生成器：本地规则渲染 / 外部模型调用与降级
  ▼
领域层（domain/）
```

### （二）为什么定义要入库

智能体的名称、目标、提示词、输出结构、可用工具、生成方式全部存放在三张表里。新增一个智能体或调整它可用的工具，只需要改数据。

这样做的好处是可以被检查：`registry.problems()` 会检出声明了却没有实现处理器的工具，以及没有绑定任何工具的智能体。若把定义写进代码，这类不一致只能靠人工发现。

### （三）三段式编排

一次调用固定为三段，每段留下一条步骤记录：

| 阶段 | 做什么 | 失败时 |
| --- | --- | --- |
| 前置工具 | 检索语料、提取推演摘要、换算金额与月数 | 必需工具失败则整体失败；非必需工具失败只记告警 |
| 生成文本 | 由 rule 或 openai_compat 产出 | 外部模型失败回落到 rule 并标记降级 |
| 合规校验 | 校验输出是否违反硬约束 | 必需校验不通过则整体失败 |

合规校验放在生成之后，是因为它校验的对象就是生成出来的文本。三条硬约束：未设置目标时不得出现任何数字；不得出现收益承诺类措辞；任何输出都必须附带免责提示。

### （四）两条生成路径的关系

rule 与 openai_compat 对外产出同一套结构，调用方不需要区分。差别只在措辞质量与是否联网。

选择哪条路径由两道闸门决定：全局是否允许联网、以及该智能体是否被指定为本地规则。两道都放行且服务地址与模型名齐备时才发出网络请求。这个设计保证了"外部接口不可用时必须降级运行"不是一句承诺，而是默认路径本身。

凭据只从环境变量读取，不写入数据库，也不进版本控制。

## 九、收支分离

### （一）旧模型的问题

旧模型里一个「生活费」数字既当收入、又当支出基准，支出被写死成「生活费乘以固定比例」。后果是：使用者无法表达自己的真实支出结构，推演出的结余是预设比例的算数。

### （二）新模型

```
收入流（可增删，年级驱动窗口）
  家庭支持 · 兼职 · 奖学金 · 实习 · 助研助教
  ─
支出项（可增删，刚需或弹性，各自增长率）
  房租 · 餐饮 · 交通 · 日用品 · 通讯  → 刚需
  学习 · 社交 · 娱乐                → 弹性
  =
结余（逐月模拟）
  → 分配到四账户：安全底座 → 成长悦己 → 体验悦己 → 长期复利
```

成长悦己与体验悦己是「存起来的储备」，支出项是「每月花掉的钱」，两者不再混淆。成长悦己只在账户分配里作为上限，不在推演里被当作支出扣除，否则同一笔钱会被算两次。

### （三）年级驱动的落地

年级字典的 attributes 里存收入窗口映射，前端选择年级时据此调整各收入来源的启用状态与时间窗口。助研助教只在研究生阶段默认启用，实习在高年级及以后默认出现。

## 十、财务画像

### （一）画像的三个财务维度

画像不按生涯路线分类，按三个财务维度描述：

| 维度 | 说明 |
| --- | --- |
| 收入结构 | 收入稳不稳定、多元还是单一 |
| 支出结构 | 刚需占多大比例、弹性空间有多少 |
| 目标时间压力 | 短期刚性目标还是长期弹性目标 |

三份内置画像分别是：多元收入型（收入多元、波动大）、高刚需型（刚需占比高、短期大额目标）、长期积累型（收入稳定低额、目标跨度长）。

### （二）画像不绑定年级

内置画像的年级字段只是推演兜底值，不再作为「这个人读几年级」的约束。前端加载内置画像时保留用户当前年级，随后按年级重算实习、助研等收入的启用状态与时间窗口。

年级覆盖与否由来源决定：内置画像不覆盖，用户档案恢复保存时记录的年级。

### （三）内置画像与用户档案

archetypes 表有 kind 列，取值 builtin 或 user。内置画像只能读、不可删；用户档案可增删改。两者共用同一套收入、支出、目标结构，区别只在来源与能否删除。

## 十一、城市变量已移除

城市变量曾以「生活成本系数」的形式参与默认收支生成：八个城市各带系数，切换城市时按「基准 × 系数」重算家庭支持与各支出项。这套系数没有权威来源，属于硬编码，且省级口径（国家统计局城镇居民人均消费支出）无法区分同省城市、也不对应学生生活费，与产品人群不符。已整体移除。

移除范围：城市字典项与字典类型、界面文案、录入页城市字段、画像的 city 字段与快照输出。archetypes 表的 city 列仅为兼容旧库保留，写入时统一补空串，不再参与任何计算。默认收支改为直接取基准值——家庭支持取参数表的全国月均生活费，各支出项取字典默认金额。

原本由城市承担的「快速起步」职责移交画像机制：载入一份内置财务画像即得到一套完整收支，比按城市系数换算更贴近真实，也不需要不可引用的数据源。
## 十二、智能体配置的存放

模型服务的参数分两层：地址、模型名、温度、超时这些非敏感项存数据库 app_settings，可导出、可迁移；凭据只落仓库之外的 .env.local（.gitignore 已忽略 .env.*），启动时载入进程环境，运行期只从环境变量读取。凭据任何情况下不返回给前端，设置页只拿到「是否存在」的布尔值。

设置页的保存走「先写后读」：写入在会话事务里完成，状态回读必须等事务提交之后用新连接做，否则读到的是旧值。连通性诊断（/agent-settings/test）走生成阶段的同一套请求路径，但只回报是否接通与失败原因，不返回模型输出——诊断不该绕过正式调用链路的合规校验。
